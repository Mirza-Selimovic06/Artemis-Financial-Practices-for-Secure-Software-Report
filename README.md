# Artemis-Financial-Practices-for-Secure-Software-Report
1. My client was Artemis Financial, a financial consulting company that provides savings, retirement, investment, and insurance planning to its customers. Because the company handles sensitive client financial data through a public facing web application they wanted their Spring Boot RESTful web application more secure. I was asked to check the application for vulnerabilities, recommended and implemented mitigations and document secure communications and data integrity practices that fit the Artemis Financials environment.
2. I ran OWASP Dependency-Check scan before making changes to initiate a baseline and to identify the outdated Spring Boot 2.2.4 parent as the root cause of many of the vulnerable libraries such as Tomcat, and other Spring components. Coding security matters especially in the finance industry because a single vulnerability can expose client data which can cause financial losses which then bring legal and regulatory consequences. Security adds value to a company by protecting its reputation and customer trust.
3. The most helpful part was checking the dependency check before and after I ran it. It helped me make sure that there was a difference before and after, as well as make sure that the vulnerabilities that I saw before were gone.
4. I added several layers of security such as secure communications by generating a self-signed certificate with Java's keytool command, data integrity by adding a checksum controller that generates a SHA-256 checksum for a data string, and I added dependency hygiene by upgrading spring boot from 2.2.4 to 2.7.18. In the future I would combine automated dependency scams, static code analysis and manual code review. I would also use a professional grade certificate from a trusted certificate authority.
5. After refactoring I rebuilt the project with Maven and made sure it ran without errors, I then visited the /hash endpoint to confirm the secure connection worked and the checksum was generated and verifies. I then re-ran the OWASP Dependency-Check scan on the refactored project and compared my new report to the old report.
6. Definitely the OWASP dependency-check would be a tool I use for future projects because it is helpful in showing what dependencies are not secure and it allows me to research and find solutions around it. For practices I would avoid weak algorithms like SHA-1 and MD5 and use trusted libraries.
7. I would show employers the before and after dependency reports and refactored code. It helps demonstrate that I can assess a real application for vulnerabilities, and implement mitigations.
